# 0008：以持久任务监督层编排运维

## 背景

一次模型回合结束不能表达多主机运维任务是否完成。运维需要关联后续输入、审批、部分失败、检查点和验收证据，同时保留已有单主机工具及安全边界。

设计参考 DeepSeek 公开的 [Super Agent 原型](https://github.com/deepseek-ai/dsh-superagent-prototype/tree/8c32a9dc5d72c033816c6a8110b37f40cf94fba4) 的持久任务、worker 会话和监督模型。

## 决定

- `rove-ops` 定义任务存储与状态，Journal Provider 持久化版本化元数据；正文、报告和检查点通过本机加密审计保存，索引只持有引用。
- 总管使用创建、查询、补充输入、重试和取消任务的工具。主机 worker 沿用 Rust `Assistant`、实时 `Policy`、SSH/SFTP 和审计。
- 一个进程中的手工与定时任务共用全局 worker 预算。同一来源请求去重，同一子任务串行执行；失败重试不重新运行已完成主机。
- 修改范围由用户明确授权并冻结。每次操作仍经过当前 Policy，改变审批模式不能扩大只读任务范围。
- 完成声明必须逐项引用本轮实际成功的工具证据；没有验收声明、请求预算耗尽、待审批和未知副作用分别保留状态。
- 重启恢复任务状态和检查点，不直接重放未确认的远端修改。用户明确核对结果后才允许继续；应用关闭后不调度。

## 取舍

原型的 DSH 执行器面向编码工作流和操作系统用户权限。引入整套 TypeScript 宿主需要重新适配工具、权限、打包及进程生命周期。RoveTerm 在现有 Rust 底座上实现任务监督，保留原有凭据和逐操作审批。

## 验证

逻辑测试覆盖来源去重、版本冲突、持久化失败、共享并发、审批中断、选择性重试、检查点与证据。脚本模型验证检查点失败时不执行工具、未知结果不重放，以及未提交逐项验收时不能完成。新旧调度的确定性对照分别记录执行次数、模型调用及并发峰值。
